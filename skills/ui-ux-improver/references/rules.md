# ui-ux-improver rules (UXI-*)

Each rule: the observable defect, the fix, how to detect it, severity, evidence. Nielsen severity (0 to 4) is assigned **after** collection: 4 -> blocker, 3 -> warning, 2 -> warning if frequent and persistent, suggestion otherwise, 1 -> suggestion. Evidence: *Consensus* (several independent sources), *Supported* (a standard or two sources), *Single source* (raise as a question if the rule contradicts the project's style guide). Related rules: UX-* and A11Y-* in `${CLAUDE_SKILL_DIR}/../unslop/references/catalogue.md`.

Contents: 1. Screen · 2. Truthful states · 3. Navigation and shell · 4. Lists, tables, filters, search · 5. Forms · 6. Modals, confirmations, messages · 7. Copy · 8. Heavy use · 9. Method · 10. Myths not to apply

## 2. Truthful states (the most serious, invisible on a screenshot taken once loaded)

| ID | Defect | Fix | Detection | Severity | Evidence |
|---|---|---|---|---|---|
| UXI-50 | While loading, the screen states something false: "0", "Nothing to do", an empty list, a goal at "+ 3 to plan" | Skeleton shaped like the content, pending values ("– / 3"), `aria-busy`; no component reads missing data as empty | Read the code: components that ignore `loading`; throttled network | Warning (blocker if the false state prompts action) | Supported: [NN/g, system response](https://www.nngroup.com/articles/response-times-3-important-limits/), UX-02 |
| UXI-51 | Swallowed error: `.catch(() => {})`, third-party failure returned as 200 `{ error }` then ignored, panels showing a false empty state next to the error message | Read the error, state it with its cause and "Retry"; dependent panels do not render; actions that depend on it are disabled with the reason | Static: `catch(() => {})`, `error` field never read; targeted `inspect.mjs --fail-api` | Blocker | Consensus: UX-03, [GOV.UK](https://design-system.service.gov.uk/patterns/validation) |
| UXI-52 | Stale data after an action or a sync: the list, counters or selectors on other screens are not re-read | Re-read after every mutation (shared event, invalidation, `router.refresh()`), including header selectors | Read the code: mutation without re-read; interaction: act, then look at the other screens | Warning | Supported: UX-09, [NN/g H1](https://www.nngroup.com/articles/ten-usability-heuristics/) |
| UXI-53 | Success announced without server confirmation (toast "Added" while the server truncated or ignored; `setTimeout` faking a call) | Success only after the response; an explicit server refusal (400 + message) instead of silent truncation | Static: `toast.success` before `await`, `setTimeout` inside a submit; network interaction | Blocker | Supported: [Hallmark](https://raw.githubusercontent.com/Nutlope/hallmark/main/skills/hallmark/references/interaction-and-states.md), UX-03 |
| UXI-55 | Derived data that does not follow its status: an item moved back to draft keeps its scheduled date and stays on the calendar and in the cadence; a counter computed from a field that the status change does not clear | One derivation function that reads the status (scheduled date only if "scheduled"), or clear the field on status change; a "draft with a date: nothing" test | Read the code: trace each displayed number and date back to its computation, then change the status | Warning | Observed in a field audit (two independent evaluators); [NN/g H1](https://www.nngroup.com/articles/ten-usability-heuristics/) |
| UXI-26 | The indicator flickers on a fast response; blocking wait for an action that almost always succeeds | Appearance delay ~150-300 ms, minimum duration ~300-500 ms; optimistic update then reconcile, roll back or offer Undo on failure | Network interaction fast then slow; static: `isPending &&` without delay | Suggestion | Single source for the values: [Vercel](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/README.md); benchmark [NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/) |
| UXI-27 | Long work (over 10 s, multi-minute generation) that blocks the page: no steps or estimate, no stop, result lost if you leave | Step n of N, estimated time, Stop, background work you can come back to, completion signal | Interaction: start, change page, come back | Warning | Supported: [NN/g progress](https://www.nngroup.com/articles/progress-indicators/), [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/loading) |
| UXI-54 | Input is lost: click on the backdrop or Esc of a modified modal, navigation, a failed submit that closes the modal | Backdrop dismissal off when the content is modified (`disablePointerDismissal={dirty}`) or a discard confirmation; the modal stays open on failure with the error near the row | Interaction; read the code | Warning | Supported: UX-05, [Shopify](https://shopify.dev/docs/apps/design/user-experience/forms) |

## 9. Method (heuristic evaluation adapted to an agent)

1. Start from tasks: for each screen, the question and the main task ("When…, I want…, so that…" format if the user talks about it) ([GitLab UX Scorecard](https://gitlab.com/gitlab-org/gitlab-design/-/issues/2553)).
2. Cognitive walkthrough of the main task, at each step: will the user try? will they see the action? will they connect it to their goal? will they see they are making progress? ([NN/g](https://www.nngroup.com/articles/cognitive-walkthroughs/)).
3. Two passes per screen: the first for flow and scope, the second element by element against the heuristics and these rules ([NN/g 2023](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)).
4. Several independent evaluators find more than one: for a full pass, successive subagents that do not read the previous report (2 in parallel at most).
5. Each finding: problem, rule, location (`file:line` or selector), fix. Heuristics are not ticked off.
6. Severity assigned after collection ([Nielsen](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)): frequency, impact, persistence.
7. Consolidate: group, deduplicate, tie to the shared component.
8. Limit: the evaluation spots potential problems; it does not replace a test with 5 users per group ([Nielsen 2000](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/)).

## 10. Myths not to apply

- "7 ± 2 menu items": not a basis for a limit; visible navigation relies on recognition ([Laws of UX](https://lawsofux.com/millers-law/)).
- "3-click rule": no data behind it; what matters is clear labels ([NN/g](https://www.nngroup.com/articles/3-click-rule/)).
- "Hick's law, so always fewer options": not to the point of hiding the navigation ([Laws of UX](https://lawsofux.com/hicks-law/)).
- "Doherty 400 ms" as a law: keep the 0.1 / 1 / 10 s thresholds from [NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/).
- "Five users find 85% of problems" everywhere: only in iterative qualitative testing, per user group.
- "F-pattern reading, so put everything on the left": the F is the symptom of badly formatted content ([NN/g](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)).
- "Dark mode is easier on the eyes": light reads better for most people; offer both ([NN/g](https://www.nngroup.com/articles/dark-mode/)).
- "Zebra-striped tables are a defect": per NN/g they help scanning; banning them is a house-style choice, not a UX rule.
